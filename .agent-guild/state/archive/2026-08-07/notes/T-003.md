## Approach

- `render_script()` renders each `.tmpl` with `HOME="$REAL_HOME" chezmoi
  execute-template <"$SRC/$tmpl"`, explicitly pinning HOME to the real one
  captured before `setup()` ever touches it (mirrors `tests/licensed-fonts.bats:22`
  but adds the explicit HOME= prefix, since install-claude-plugins needs the real
  `~/.config/chezmoi/key.txt` to render any install calls at all). `setup()`
  separately exports a synthetic `$HOME` for the actual script execution, so
  render and execute never share an environment.
- PATH is scoped per `run` invocation, not globally: `$STUBS:/usr/bin:/bin` for
  packages/vscode/claude-plugins (hides brew/code/claude, which don't live in
  those two system dirs, while keeping awk/mktemp/tee/grep available), and
  `$STUBS:/bin` for raycast (excludes /usr/bin, since `open` is a macOS system
  binary at /usr/bin/open — the only one of the four tools that's already on a
  minimal PATH, so it has to be excluded specifically for the absent-tool case
  to mean anything).
- vscode/raycast "present tool failing" and "keeps going" cases read the real
  extension lists (`dot_config/vscode-extensions.txt`,
  `dot_config/raycast-extensions.txt`) rather than hardcoding ids, so the tests
  track the roster instead of drifting from it. claude-plugins identifiers come
  from grepping the *rendered* script for `add_marketplace`/`install_plugin`
  lines, since the manifest is age-encrypted and only readable post-render.
- Stubbed `defaults` (recording invocations to a log file) in all four raycast
  cases per D-4, and stubbed `sleep` as a no-op in the three raycast cases that
  drive the full ~27-item loop, since the script sleeps 1s per item and nothing
  under test depends on the wait.

## A real bug I hit and had to design around

bash 3.2 (`/bin/bash`, what this machine's `bats` runs test bodies under) has a
genuine `errexit` quirk: a failing `[[ ... ]]` does **not** abort a function
unless it's the function's literal last statement. Confirmed directly:
`set -e; f() { [[ 1 -eq 2 ]]; echo reached; }; f` prints "reached" on this
machine. `[ ]` (single bracket) and plain external commands don't have this
problem — only `[[ ]]`.

This silently broke my first draft: any test with more than one `[[ ]]`
assertion only actually enforced the *last* one, so an early "did this fail
correctly" check could be false and the test would still report ok, masked by
a later assertion that happened to be true in both baseline and HEAD. I found
it because two baseline-mutation cases passed when the table said they should
fail (the discriminating assertion wasn't the last line).

Fixed it by replacing every substring check with two small helpers,
`assert_contains`/`assert_not_contains`, built on `grep -qF` and a `case`
statement rather than `[[ ]]`. Both were verified by hand to propagate
`errexit` correctly regardless of position in the test body. I did not touch
any other `.bats` file in this repo, so I don't know whether this bug affects
existing multi-assertion tests elsewhere — flagging it in case that's worth a
separate look, since it's a correctness gap wider than this one file.

## Other judgment calls

- Raycast's "all items succeed" case doesn't assert on the success wording
  ("Raycast install requests sent...") because that message was reworded by
  the conversion (baseline said "Raycast configuration complete."), and V-1's
  table requires this case to *pass* at baseline as a regression guard. Only
  the negative assertion (no failure heading) and the defaults-stub proof are
  checked, matching the same shape as the install-packages all-succeed case.
- For "present tool failing names the item" on vscode/claude-plugins, I
  deliberately assert on the failure-summary's exact formatted line (e.g.
  `raycast://extensions/install/$ext`, `plugin $spec`) rather than the bare
  identifier, because the bare id also appears in progress-echo lines that
  already existed at baseline — asserting on the bare id alone would have made
  those cases pass vacuously at baseline instead of failing as the table
  requires.
