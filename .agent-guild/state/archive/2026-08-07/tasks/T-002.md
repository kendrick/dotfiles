## Spec excerpt

A failed package install is currently indistinguishable from a clean one. On
2026-08-06, `fzf` was added to the `core` bundle, `chezmoi apply` ran,
`install-packages.sh` recorded itself as done, and `fzf` was never installed.
Nothing errored and nothing retried, because from chezmoi's point of view the
script succeeded. The line responsible:

```bash
brew bundle --file=/dev/stdin <<<"$brewfile" || echo "Some Brewfile entries failed (MAS apps may need manual install)."
```

The guard is deliberate and mostly right — a machine without `code` on `PATH`
must not abort an apply. The defect is that "the tool isn't here, skip" and "the
tool ran and could not do the job" produce the same output. Only the second is a
problem, and it is the one being hidden.

**Convert all four sites.** Converting a subset fails clause B-1.

| Script | Install call | Currently |
| --- | --- | --- |
| `run_onchange_install-packages.sh.tmpl` | `:31` `brew bundle` | `\|\| echo "Some Brewfile entries failed…"` |
| `run_onchange_install-vscode-extensions.sh.tmpl` | `:21` `code --install-extension` | `2>/dev/null \|\| true` |
| `run_onchange_configure-raycast.sh.tmpl` | `:22` `open "raycast://…"` | `2>/dev/null \|\| true` |
| `run_onchange_after_install-claude-plugins.sh.tmpl` | `:34` marketplace add, `:41` plugin install | `2>/dev/null \|\| true` |

`run_onchange_after_restore-agent-skills.sh.tmpl:87` is the closest thing to the
target shape already, and it names its source in the message. Read it first.

**What each script must do.** The full contract is clause B-2; this is the
summary a worker needs:

1. **Tool absent** — print a message naming the missing tool, say it skipped,
   exit 0. Three sites already do this. `configure-raycast` does **not**: `:12-13`
   is a bare `exit 0` that prints nothing, and it gains a message.
2. **Tool present, item failed** — the script's own summary names the failing
   item. Not a count, not "some entries failed", not the CLI's raw stderr alone.
   Identifiers: formula/cask/`mas` name for brew, extension id for code, plugin
   spec or marketplace name+repo for claude, and for raycast the `raycast://` URL
   or slug — but only where `open` itself refused the URL.
3. **The two read differently** — a reader tells skip from failure by wording
   alone, without exit codes. Neither borrows the other's phrasing.
4. **A clean run says nothing about failures** — no empty summary, no bare
   heading, no "0 failed".
5. **The reason survives** — stop discarding the tool's error output.
   `spec.md:48` singles out the vscode site for throwing away "the error text as
   well as the exit code". Either stderr reaches the run's output, or the script
   captures it and includes it alongside the item name.

**Keep going, and report once.** A failing item must not stop the rest. This
governs the three multi-call sites: `install-vscode-extensions` and
`configure-raycast` loop; `install-claude-plugins` renders a flat sequence of 7
`add_marketplace`/`install_plugin` calls. `install-packages` is exempt — it is
one `brew bundle` invocation and brew already continues internally; its only
obligation is naming.

Note that **continuation already works today** — `|| true` is what provides it.
Measured at baseline, the rendered vscode script attempts all 43 extensions and
exits 0. What you are adding is the *collected end-of-run summary*, not the
continuation. Do not break the continuation while adding the summary.

**Always exit 0.** Every branch: tool absent, everything succeeded, some items
failed. The apply must not abort — `spec.md:58` requires it, and the non-goal at
`spec.md:79` explains why. The issue's title reads "Failed installs exit 0" as a
description of the *bug*; do not "fix" it by making the scripts exit non-zero.
That would abort every apply on any machine missing any package.

**Raycast can only claim what it can see.** `open raycast://...` hands the URL to
macOS and returns before any install happens. Distinguish an absent `open` from
`open` refusing the URL, and say nothing about whether an extension installed.
Leave a comment recording why that site can go no further.

**bash 3.2.** `/bin/bash` is 3.2 here. Guard every array expansion with
`[ "${#arr[@]}" -gt 0 ]` before `"${arr[@]}"`. None of these scripts sets `-u`,
so an unguarded empty expansion does not abort — it prints a blank line, which
reads as a failure with no name attached and contradicts requirement 4. No
associative arrays, no `${var^^}`. Do not rely on `errexit` behaving through
`|| true`; that is unreliable for external commands on 3.2 and is documented at
`run_onchange_after_install-global-node-packages.sh.tmpl:32-33`.

**Comments.** Explain why the code has this shape — the incident, the
constraint, the thing a reader would otherwise reintroduce. A comment restating
what the line does fails clause B-6. The existing headers on these scripts are
the register to match.

**One `|| true` stays.** `brew trust --tap "$tap" 2>/dev/null || true` at
`install-packages.sh.tmpl:27` is not an install call — it pre-trusts taps so
`brew bundle` does not abort on the first tapped entry. Leave it.

**Do not touch** `run_once_after_configure-macos.sh` (its eight `|| true` guards
are settled, see `_working-memory/antipatterns.md:71-75`), `dot_local/`, or
`.chezmoidata.toml`. Do not run `chezmoi apply`, install anything, or push.

**Orchestrator ruling: checker of record upheld.** Read against the clause text directly:

B-2 requirement 2 forbids "a count, a generic 'some entries failed', or the CLI's raw stderr alone." The degenerate line is none of the three. It carries no count. It is not a euphemism for failure — it states specifically that brew exited non-zero *and* emitted nothing matching the shape that names entries, which is information about the parse rather than a substitute for it. And it points at raw output that is present in addition, not in place of, a summary.

The requirement is also conditioned on an individual item failing identifiably. In this branch brew did not emit an identifiable entry, so no identifier exists in the script's input. A clause cannot require the script to print a name its input never contained. The only alternative in that branch is printing nothing, which is precisely the silence the job exists to end.

**But the courier's underlying concern is legitimate, and worth more than its stated finding.** The parser matches brew's `<Verb> <entry> has failed!` shape. If brew's output format drifts, the parser silently stops matching and *every* failure degrades to the degenerate line — at which point B-2's naming protection is gone with nothing signalling that it is gone. That is an undetected-regression risk, not a defect in this artifact. It belongs in a follow-up issue: either a test pinning brew's failure-line shape, or a louder degenerate message that reads as a bug report rather than a status line.

**Clause type: B-2 and B-6 are judgment rubrics** — the first crossing in this job where agreement was not guaranteed by construction. The disagreement is a genuine interpretive split on an edge case where real tool behaviour (unparseable output) meets an idealised requirement (always name the item), which is exactly the variance #34 exists to measure. Count this one.
