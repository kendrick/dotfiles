## Spec excerpt

Acceptance criterion 8 requires new coverage for both branches — tool absent, and
tool present but failing — driven by stubs rather than a real failed install.
This task writes that coverage. `tests/doctor.bats` is the stub-on-`PATH` harness
to follow.

**Fifteen cases, titled exactly so a checker can find them:**

- `<script>: absent tool skips clean` — one per site, four total
- `<script>: present tool failing names the item` — one per site, four total
- `<script>: one failure does not stop the rest` — one per multi-call site
  (vscode, raycast, claude-plugins), three total
- `<script>: all items succeed prints no failure summary` — one per site, four
  total

Every case asserts `status -eq 0`. That assertion is not decoration: it is the
only thing preventing a conversion that names failures correctly and then aborts
the user's entire `chezmoi apply`. No case may assert a non-zero status.

**Render and execute in different environments.** This is the part that is easy
to get wrong.

Render the templates first with `chezmoi execute-template`, the pattern
`tests/licensed-fonts.bats:22` already uses. Never assert against a raw `.tmpl`.

Rendering must happen under the **real** `$HOME`, because
`run_onchange_after_install-claude-plugins.sh.tmpl` gates on
`~/.config/chezmoi/key.txt` at `:62` and falls to an `else` branch at `:76`
without it. Measured: real home renders 7 install calls, a synthetic home renders
0. If you render under the fake `$HOME`, the two claude-plugins cases have
nothing to drive and will pass vacuously.

Then *execute* the rendered script under the synthetic `$HOME` with stubs on
`PATH`. Render-time and execution-time environments are separate concerns.

**Resolve scripts relatively.** Locate the repo as `SRC="${BATS_TEST_DIRNAME}/.."`.
Do **not** use `chezmoi source-path` — `tests/doctor.bats:33` stubs it — and do
not use absolute paths. If you do, the baseline mutation check silently renders
the converted scripts inside the baseline worktree and passes green while proving
nothing.

**Stub `defaults`.** `run_onchange_configure-raycast.sh.tmpl:30` runs
`defaults write com.raycast.macos raycastGlobalHotkey`, which ignores `$HOME` and
writes to the real `~/Library/Preferences`. Any case executing that script must
have a recording `defaults` stub on `PATH`, or the suite rewrites the user's
actual Raycast hotkey on every run. It also dies at 127 under `set -e` without
one, so the case cannot assert `status -eq 0` anyway.

**Expected outcomes at baseline (`1dec91c`).** The checker compares each case's
TAP line against this. Getting a row wrong fails the task even if the case is
otherwise well written.

| Case | At baseline |
| --- | --- |
| `install-packages: absent tool skips clean` | pass |
| `install-vscode-extensions: absent tool skips clean` | pass |
| `install-claude-plugins: absent tool skips clean` | pass |
| `configure-raycast: absent tool skips clean` | **fail** |
| all four `present tool failing names the item` | **fail** |
| all three `one failure does not stop the rest` | pass |
| all four `all items succeed prints no failure summary` | pass |

Two rows deserve explanation.

*Raycast's skip case fails at baseline* because `:12-13` is a bare `exit 0` that
prints nothing. The other three sites already print a skip message, so their
cases pass unchanged.

*The keeps-going cases pass at baseline* because `|| true` already provides
continuation — measured, the rendered vscode script attempts all 43 extensions
and exits 0. These three are regression guards: they protect behaviour that
already works and that the conversion could break. Do not contort them into
failing at baseline by smuggling in a naming assertion; that duplicates the
`names the item` cases and is the contradiction that failed three earlier
constitution revisions.

**Do not** run `chezmoi apply`, edit `.chezmoidata.toml`, install anything, or
push. Everything is proven with stubs.

**What this says for #34, and it cuts against my own expectation.** I briefed this crossing as low-value because V-1, B-3 and D-4 are deterministic and both parties would read the same captured output — agreement by construction. That reasoning was wrong in an important way. When the orchestrator composes the evidence packet rather than the vendor running the checks, a deterministic clause does not guarantee agreement; it relocates the failure mode from *judgment* to *transcription*. The courier could not catch a bad test, but it did catch a bad number, and the bad number came from the checker of record via me.

Two process lessons, both mine:

1. **Inline raw command output, never a prose summary of it.** Minor #2 named this directly. A summary is a transcription step, and transcription is exactly what failed here.
2. **A checker's narrative count deserves the same scepticism as a worker's self-report.** I accepted "7 pass, 8 fail, exactly as specified" without arithmetic, and the constitution's own table would have caught it in one subtraction.

**Lane reliability finding.** The verdict JSON at this stem is malformed and does not parse: unescaped inner double quotes in the `description` field (`all three "one failure does not stop the rest" cases`), breaking at char 216. `validate-verdict.py` rejects it. The rendered `.md` sibling is intact and readable, which is the only reason the finding was recoverable at all.
