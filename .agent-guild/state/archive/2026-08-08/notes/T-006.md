# T-006 rework notes (sonnet r1)

## What changed

Widened the guard's grep pattern in `tests/lint.bats` from first-token-only
to command-position-anywhere, per the diagnosis. Final pattern:

```
(^[[:space:]]*|;[[:space:]]+|&&[[:space:]]+|\|\|[[:space:]]+|\{[[:space:]]+|\bthen\b[[:space:]]+|\bdo\b[[:space:]]+|\belse\b[[:space:]]+)(\[\[|\(\()
```

Deliberately excludes `if`/`elif`/`while`/`until` as triggers — `[[`/`((`
right after those is a safe condition (its exit status controls the branch
regardless of the bash 3.2 bug), and `tests/mutation-check.sh` uses that
idiom for real (`if [[ "$text" =~ ... ]]; then` at lines 168, 172, 287). A
pattern that flagged those would turn the suite red on legitimate code, not
just canaries.

## Two problems found and fixed beyond the diagnosis's own trigger list

The diagnosis specified the trigger set (`;`, `&&`, `||`, `then`, `do`,
`else`, opening brace) but not the spacing rule between a trigger and the
bracket. My first attempt used `[[:space:]]*` (zero or more) uniformly,
which broke in two ways I found only by running the pattern against the
real surface and against itself, not by inspection:

1. **False positive on real code.** `tests/mutation-check.sh:168` has
   `\{[[:space:]]*$` — an escaped brace opening an ERE interval, directly
   against a `[[:space:]]` character class, zero spaces between. A `{`
   trigger with optional spacing matched it.
2. **The guard flagged its own pattern-definition line.** The pattern
   string itself necessarily spells `;[[:space:]]`, `&&[[:space:]]`,
   `\{[[:space:]]`, etc. — every trigger written directly against the
   literal `[[` with zero spaces, because that's what the regex syntax for
   "space class" looks like. Optional spacing matched every one of them.

Fixed both by requiring **mandatory** whitespace (`+`, not `*`) between
every mid-line trigger and the bracket — real shell code always writes a
space there (`; [[`, `&& [[`, `{ [[`; `then`/`do`/`else` need a delimiting
blank to parse as reserved words at all), so this costs no coverage against
anything in the corpus or against the diagnosis's own three example
plantings, all of which have a space. It does mean a hypothetical
zero-space form like `;[[ 1 -eq 1 ]]` (valid but unidiomatic bash) would go
undetected — flagging this as the judgment call the task instructions ask
for. `^` (true line start) keeps `[[:space:]]*` since it's about
leading-indentation, which is legitimately variable.

Comment-only lines (first non-whitespace char `#`) are filtered out after
the match via a second grep pass, using the same `X="$(...)" && s=0 || s=$?`
errexit-safe idiom as the rest of the file — this is what lets the file's
own header prose and the worked examples in `tests/helpers.bash` /
`tests/mutation-check.sh` describe the bug (including with `;` and `{` in
their text) without self-matching.
