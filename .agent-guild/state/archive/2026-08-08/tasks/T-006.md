## Spec excerpt

Write `tests/lint.bats`, a bats case that fails the suite if a bare `[[` or `((` statement is ever reintroduced.

**Why this is a test and not a script.** The 54 assertions this job converted were the ones that existed; 30 of them were safe only because nothing followed them in their block, and appending a single line to any of those blocks would have disarmed the assertion above it with nothing to catch it. The guard lives inside the suite so that `bats tests/` alone catches a regression — no second entry point for CI or a contributor to forget.

**What to scan.** Exactly three globs, which the constitution calls the guarded surface:

- `tests/*.bats`
- `tests/helpers.bash`
- `tests/mutation-check.sh`

**`tests/mutation-check.sh` already exists when you start** — T-007 builds it and this task depends on that, deliberately. If you ran first, your guard would scan a path that does not exist, `grep` would exit 2 rather than 1, and a guard that reads "non-zero means clean" would pass vacuously over a third of its own surface while reporting green. The ordering also protects T-007: if `lint.bats` existed while that script enumerated helper calls, any helper call in your file would inflate its pinned per-file counts.

The two non-`.bats` files matter as much as the rest. `helpers.bash` is the one place a single `[[` would disarm every call site in the suite at once, and `mutation-check.sh` runs under the same bash 3.2 and has the same bug. A guard that scans only `*.bats` is this task's stated failing example.

**What counts as a violation.** A line whose **first non-whitespace token** is `[[` or `((`:

```bash
/usr/bin/grep -nE '^[[:space:]]*(\[\[|\(\()' <files>
```

First-token is the whole trick, and it is not negotiable. A naive `grep '\[\['` over this suite returns five hits that are not commands: a `grep -oE` regex at `apps.bats:50`, `[[:space:]]` classes inside single-bracket tests at `font.bats:460` and `packages.bats:105`, and two comment lines at `install-failures.bats:68` and `:71` that quote `[[ ]]` while describing this very bug. First-token excludes all five. It is also what lets this file contain the pattern it forbids without flagging itself.

**Resolve paths from `BATS_TEST_DIRNAME`**, never `$PWD` and never an absolute path. The check that verifies this guard copies the suite into a scratch worktree and plants canaries there; a guard that resolves through `$PWD` scans the real working tree instead, finds it clean, and reports green no matter what was planted. The previous job hit exactly this and wrote it down.

**Keep it to one `@test` case.** This file is new and additional to the suite's per-file floors, so its case count is not pinned by anything — but T-009 verifies the assembled suite and one case is the number it will expect. If you have a reason to write more than one, say so in your report.

**Failure output should name the offenders.** A bare "found a bare bracket" sends the next contributor hunting; print the `file:line` hits so the fix is obvious.

**Write a comment explaining why the rule exists** — the bash 3.2 mechanism, not the regex. The comment at `tests/install-failures.bats:67-72` is the register to match; it explains the bug better than the issue does.

**Do not** convert anything, touch another test file, or add an exemption for `||`-suffixed lines. `packages.bats:146` was converted in T-005 to single-bracket precisely so this guard could stay an absolute zero with no exemptions — an exemption is a hole someone later walks through with `[[ ... ]] || true`.

**Verify before reporting done.** The suite must be green with the guard in place, and the guard must actually fire. Test all three file kinds, restoring with `cp` from the real tree rather than `git checkout` — before the job's commit lands, `git checkout` restores the *baseline*, which puts genuine bare `[[` back into `jsonc.bats` and makes your guard look like it works when it does not:

```bash
bats tests/lint.bats                            # exits 0
bats tests/                                     # whole suite still green
printf '\ncanary() {\n\t[[ 1 -eq 1 ]]\n}\n' >> tests/helpers.bash
bats tests/lint.bats                            # MUST fail
cp <original> tests/helpers.bash                # restore, not git checkout
```


## Rework diagnosis

### sonnet r0 — orchestrator ruling, not a checker FAIL

The checker of record passed this task, and its check was faithful to what `check_method` asked. The defect is in the guard, and I confirmed it directly rather than taking a report on trust. The `codex` courier surfaced it first and died on an API limit before persisting its verdict, so this ruling stands on my own measurement.

**The guard misses a bare compound that is not the first token of its line.** Measured on this machine's bash 3.2.57:

```
true; [[ 1 -eq 2 ]]; echo reached      -> prints "reached", exits 0   (bug present)
if true; then [[ 1 -eq 2 ]]; fi        -> prints "reached", exits 0   (bug present)
true && [[ 1 -eq 2 ]]                  -> prints "reached", exits 0   (bug present)
```

Each of those is a bare `[[ ]]` statement whose failure bash 3.2 discards, which is precisely what V-1 exists to prevent. The current pattern, anchored with `^[[:space:]]*`, returns **zero matches** for all three.

V-1's text is unambiguous: the guard fails the suite "if a bare `[[` or `((` statement is reintroduced anywhere on the guarded surface." A statement after a `;` is on the surface. The guard as written does not satisfy the clause.

**Widen the match to catch a compound in command position, not only at line start.** It must fire when `[[` or `((` begins a command anywhere on the line — after `;`, `&&`, `||`, `then`, `do`, `else`, or an opening brace. Verified before writing this: a widened pattern of that shape produces **zero hits across the entire current surface**, so this costs no false positives and no rework elsewhere.

Two things that must survive the widening, both of which the narrow pattern got right and which are easy to break:

1. **The guard must still not flag its own source.** `tests/lint.bats` necessarily contains the pattern it forbids as literal text inside a quoted grep expression. First-token anchoring is what protected it before; whatever you widen to must protect it some other way, and you must verify it by running the guard against the converted suite and requiring `ok`.
2. **The five known non-commands must stay unflagged**: the `grep -oE` regex at `apps.bats:50`, the `[[:space:]]` character classes inside single-bracket tests at `font.bats:460` and `packages.bats:105`, and the two comment lines at `install-failures.bats:68` and `:71` that quote `[[ ]]` in prose. A naive widening that matches `[[` anywhere on a line hits all five and turns the suite red.

`[[ ... ]] || continue` is not a concern and needs no exemption. That form has `[[` as its first token, so it is already caught, and T-005 converted the suite's only instance to single-bracket precisely so the guard could stay exemption-free.

**Re-verify all four original plantings plus three new ones** covering `;`, `then`, and `&&`. Restore between plantings with `cp` from the working tree, never `git checkout` — the job is still uncommitted.

None on the deliverable. Passed its checker of record on the first dispatch, all four plantings.

One process note, not a worker failure: the checker's first verdict write produced invalid JSON and had to be re-emitted. It had embedded the grep pattern it ran — `\[\[|\(\(` — literally into a JSON string, where `\[` is not a valid escape. The check itself had completed; only the transcription failed. This is agent-guild#112's failure mode, and the specific trigger is worth recording: a deterministic checker's evidence field naturally quotes the regex it executed, and any regex with a backslash breaks hand-written JSON. It will recur on every deterministic check whose clause uses a pattern, which in this constitution is most of them. The fix was a re-emit through `json.dump`, with no judgment, finding, or outcome altered.

The worker also hit an errexit bug while building the guard, which is worth keeping: its first draft used `hits="$(grep ...)"` followed by a separate `local status=$?`. Under bats' `set -e` a bare command-substitution assignment propagates the substitution's exit code to the statement, so grep's clean-pass exit 1 aborted the case before `status` was read, and the guard reported `not ok` unconditionally. Folding it into `hits="$(...)" && status=0 || status=$?` puts the code in a conditional context that `set -e` leaves alone. Same errexit-swallows-a-result family as the `[[ ]]` bug this job exists to fix, reached through a different construct, found while building the tool meant to prevent it. Documented inline in the guard.

## Orchestrator ruling on the residual zero-space gap

The worker disclosed, rather than hid, that mandatory whitespace between a trigger and the bracket leaves `true;[[ 1 -eq 2 ]]` uncaught. I verified it: that form is valid bash, is swallowed under 3.2 exactly like the spaced form, and the shipped guard does not flag it.

**Ruled acceptable, and the guard ships as written.** I tested the obvious refinement — requiring a non-colon after `[[`, since a POSIX class always has `:` there — and it does close the gap while still correctly skipping `if [[ ... ]]` conditions and the five known non-commands. But it then fires on `tests/helpers.bash`'s own comment, which quotes `set -e; f() { [[ 1 -eq 2 ]]; echo reached; }` as prose. Closing that needs comment-aware parsing, and a comment stripper that has to reason about `#` inside heredocs and quoted strings has failure modes worse than the gap it fixes.

**The line I am drawing, since I failed the spaced form and am passing this one.** `true; [[ x ]]` is ordinary shell that a person or an agent would write without thinking. `true;[[ x ]]` is not idiomatic, and a formatter normalizes it away. The guard is defence in depth against casual reintroduction; `tests/mutation-check.sh` is what actually proves assertions still fail. A guard that catches every form a human would plausibly write, and misses one nobody writes, is doing its job.

That is a judgment call and it could be wrong — the same reasoning about what "nobody writes" is exactly what made the original first-token version look sufficient. It is recorded here rather than buried so a future reader can overturn it with evidence rather than rediscover it.

## Two further gaps, found by the r1 crossing and ruled the same way

The r1 courier hit the codex lane's quota and delivered no verdict, but it tested four candidate evasions locally first and reported them. I re-derived all four. **Two are real and two are not**, which is worth stating precisely because a courier's claim is not evidence until it is checked:

| claimed | failure swallowed? | a statement? | verdict |
| --- | --- | --- | --- |
| `true \| [[ 1 -eq 2 ]]` | **no**, propagates | — | not a gap |
| `true & [[ 1 -eq 2 ]]` | yes | yes | **real gap** |
| `: [[ 1 -eq 2 ]]` | yes | **no** | not a gap |
| `case x in x) [[ 1 -eq 2 ]] ;; esac` | yes | yes | **real gap** |

The pipe case aborts correctly, so there is nothing to catch. `: [[ 1 -eq 2 ]]` runs `:` with `[[ 1 -eq 2 ]]` as its arguments — `[[` is a reserved word only in command position, so after a command name it is an ordinary word, the test never executes, and the line asserts nothing whether or not it is flagged. Reporting it as a swallowed assertion was a misreading of what bash does with it.

The other two are genuine: a bare compound after a background `&`, and one inside a `case` arm, are both statement positions whose failure bash 3.2 discards and which the widened pattern does not match. Neither form appears anywhere on the current surface.

**Ruled acceptable, and the guard ships.** The boundary I am drawing, which is the same one as for the zero-space form and is now general enough to state once: **this guard catches every form present in the corpus and every form idiomatic test code would use. Complete coverage of statement position requires parsing shell, not matching it.** A regex can be widened until it collides with the character classes and quoted patterns the corpus genuinely contains — I hit exactly that collision when trying to close the zero-space gap — and each widening buys a rarer construct at the cost of a more fragile pattern.

That is a real ceiling rather than an excuse, and the honest response is a follow-up issue proposing a parser-based check (shellcheck's SC2288 family, or `bash -n` with an AST walk) rather than another turn of the regex screw. Recorded as a candidate.

**What actually protects the suite is `tests/mutation-check.sh`**, which proves every one of the 53 assertions still fails when inverted. The guard is a tripwire against casual reintroduction, and it is worth being clear about which of the two is load-bearing.
