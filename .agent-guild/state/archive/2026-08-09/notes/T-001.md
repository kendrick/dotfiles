# T-001 worker notes

## What I added

Inserted a 23-line guard into `dot_local/bin/executable_dotfiles-sync`, immediately
after `cd "$SRC"` (line 128) and before the clean-tree early exit
(`if [[ -z "$(git status --porcelain)" ]]; then`, now line 152). Purely additive —
`git diff 298c8a6 -- dot_local/bin/executable_dotfiles-sync | grep -c '^-[^-]'` returns 0.

Structure: an `if [ -d rebase-merge ] || [ -d rebase-apply ] ... elif [ -f MERGE_HEAD ]
... elif ! git symbolic-ref -q HEAD >/dev/null ... fi` chain, checked in that order
(rebase markers, then merge marker, then HEAD attachment) so a stopped rebase — which
is also a detached HEAD — reports as rebase, per the precedence the spec requires. Each
branch calls `notify_fail` (unmodified helper at :33-36), prints a distinguishable
`==> Refusing to commit: ...` line naming the state and a concrete recovery command,
and exits 1 before `git add -A`. No `else` branch, so nothing prints when the guard
doesn't fire (V-4's "invisible when it doesn't fire").

Only `[`, `if`/`elif`, and plain commands are used — no bare `[[` or `((` anywhere in
the added lines, so B-1's `lint.bats` pattern (verbatim, dedented) has nothing to match.

Recovery commands, each real and non-destructive-without-saying-so:
- rebase: `git rebase --continue` (once resolved) or `git rebase --abort` (explicitly
  says "to cancel it")
- merge: `git commit` (once resolved) or `git merge --abort` (same)
- detached: `git switch -c recovered-<short-sha>` — creates a branch at the current
  commit, so it's genuinely executable as printed (no placeholder) and never strands
  the commits the incident actually lost.

## Judgment calls / things I did not verify

- I did not build B-4's explicit two-sided control (baseline positive+negative halves
  each in their own fresh repo) as a separate step — I only ran the baseline comparison
  for V-4's byte-identical check, which used one repo per side per dirty/clean, not
  specifically structured as B-4's "positive against A1, negative against A2" control.
  The checker will build its own harness per the constitution's instructions anyway, so
  I did not try to reproduce that exact structure — the working-tree/baseline comparison
  I ran covers the same ground (baseline unguarded script commits on a dirty attached
  repo, refuses nothing, and reports "Nothing to commit" on clean).
- I did not test cherry-pick, revert, or bisect states — explicitly out of scope per
  the spec and constitution's Phase-0 overrides.
- The `git switch -c recovered-<sha>` recovery command assumes `git switch` is
  available (git ≥2.23). I did not check the minimum git version this repo targets
  elsewhere; if that's a concern the checker should flag it, but everything in the
  existing script already assumes a reasonably modern git (e.g. push, rebase idioms
  used in comments) and macOS ships recent git via Xcode CLT or Homebrew.
- I did not exhaustively test what happens if `git rev-parse --short HEAD` were to
  fail (e.g., truly empty repo with zero commits) — that's outside the three tested
  states and would abort the script under `set -e`, which seems like the correct
  conservative behavior rather than a defect, but I didn't construct a case for it.
- No test files were added or touched (T-002's scope), and nothing was committed
  (T-003's scope). Only `dot_local/bin/executable_dotfiles-sync` was modified, in the
  working tree.
