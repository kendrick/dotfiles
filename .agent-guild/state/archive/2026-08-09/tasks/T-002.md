## Spec excerpt

Write the bats coverage for the guard T-001 added to `dot_local/bin/executable_dotfiles-sync`, and the harness it runs under. Both land under `tests/`.

**Why the harness is most of this task.** Six phases run before the guard, printing their headings at `:39`, `:57`, `:65`, `:75`, `:85` and `:103`. A test that does not neutralize them never reaches the guard at all, and one that neutralizes them badly produces cases that pass for reasons unrelated to the code under test. Two failures of exactly that kind have already been measured against draft harnesses for this job, so treat the harness as the deliverable and the cases as what it enables.

**The stub contract**, all of it required:

- `chezmoi` stubbed, handling `source-path` with no arguments (prints the scratch repo path), `re-add` (exit 0 — the call at `:66` is **not** guarded by `command -v` and aborts the whole run on failure), `status` (empty output, consumed by the loop at `:87-95`), and `source-path <path>` (exit non-zero, so the drift loop takes its `|| continue` at `:90`).
- `code`, `brew`, `jq`, `claude-plugins-capture` and `claude-settings-normalize` **absent** from the stub `PATH`, so each guarded phase takes its documented skip branch. `code` matters most, and not for the obvious reason: a failed redirect there does not abort under `set -e`, it prints and continues. The hazard is that if `$SRC/dot_config/` exists, the phase writes `vscode-extensions.txt` into the scratch repo and turns a clean case dirty.
- `osascript` stubbed to a no-op that records its **full argument list**, not merely that it ran. A `touch "$REC"` stub makes the notification's title unreadable, and the title is the only thing separating `notify_fail` at `:33-36` from the bare `notify` at `:28-31`.
- `date` stubbed to a fixed value. `:142` builds the commit subject from `$(date -u +%Y-%m-%d)`, which no `GIT_*_DATE` variable reaches, and because that token is part of the commit message it changes the commit id.
- `DOTFILES_AUTO_PUSH` left unset, so the opt-in branch at `:159` runs as it ships.
- `HOME` redirected, so `$HOME/.local/state/dotfiles/last-sync.log` is a scratch path.
- **The stub `PATH` is authoritative, not prepended**: `export PATH="$STUBS:/usr/bin:/bin"`, the form at `tests/apps.bats:73`. Do **not** copy `tests/doctor.bats:62`, which writes `PATH="$STUBS:$PATH"`. Appending the inherited `PATH` means a tool this contract requires to be absent still resolves to the real binary — the exact defect #17's T-001 fixed in `apps.bats` after a removed `fzf` stub kept resolving and hung the suite. Verified against a draft of this job's harness: under the prepending form, an **unguarded** script produced exit 1 with commit count and staged paths unchanged, which satisfies every assertion a blocked-state case makes.
- `$STUBS` and the redirected `$HOME` live **outside** the scratch repo. Inside, they leave `?? stubs/` in the porcelain and turn every clean case dirty.

**Every case gets its own freshly built scratch repo, with a bare origin**, so the push path's opt-in branch has a remote to reason about. Not a reset, not a clean. `git reset --hard` and `git clean -xdff` touch nothing under `.git/`, so `.git/rebase-merge` and `.git/rebase-apply` survive into later cases and a merge case then reports the rebase state. And a refusing case leaves its dirty marker behind by design, since the guard refuses instead of committing, so case *n*'s leftovers become case *n+1*'s starting state.

**The committed cases**, at minimum all four:

1. **Attached, no operation in progress** — the run commits normally. This one is easy to forget and is required by the spec's own acceptance criteria; without it the suite covers only refusals.
2. **Detached HEAD.**
3. **Rebase in progress.**
4. **Merge in progress**, whose marker must be built with `git rev-parse HEAD > .git/MERGE_HEAD`. An empty `MERGE_HEAD` makes `test -f` succeed while `git rev-parse --verify -q MERGE_HEAD` fails, so an empty marker decides the case's outcome by construction rather than by the guard's correctness.

**Each case drives the real script.** Do not reimplement the guard's logic in the test file and assert against the copy — that proves the copy. Nothing may reach the real `~/.local/share/chezmoi` on any path, including one where a stub silently fails to take effect.

**Each blocked-state case asserts the state it names, not just a non-zero exit.** Four cases asserting only `[ "$status" -ne 0 ]` pass the mutation check below and leave the shipped suite unable to notice a guard that reports every state as the same one. The distinguishable per-state messages are the behavior most worth locking in, because they are the part a transient checker probe verifies once and the suite would otherwise never see again. Use `assert_contains` against the message for that state, and assert the other two states' strings are absent.

**Each blocked-state case must go red when its guard is removed.** Verify that yourself before reporting done:

1. Copy `dot_local/bin/executable_dotfiles-sync` to a path **outside the repo**. This is your only restore path, so take it first and confirm it exists before touching anything.
2. Delete one detector from the working-tree script, run the suite, confirm that detector's cases report `not ok` and the others stay green.
3. Restore from your copy, and **verify the restore**: `diff` the script against your copy and confirm it is byte-identical before moving to the next detector.

Never `git checkout` here. The job's work is uncommitted while you run, so a checkout restores `298c8a6` and silently reverts T-001's entire guard rather than the one detector you deleted — and with no copy taken, that is unrecoverable.

This step temporarily edits a file outside your scope, which is deliberate and is the one exception to the boundary below. The script must be byte-identical to how you found it when you report done.

**Constraints.**

- **Ship** only files under `tests/`. `dot_local/bin/executable_dotfiles-sync` is T-001's and is finished; commits are T-003's. The mutation step above is the sole exception, and it must leave that file byte-identical to how it found it — verify with `diff` against your copy, and report the script's state explicitly when you finish.
- Do not delete or modify a line in any pre-existing test file. Add new files.
- bash 3.2, and `tests/lint.bats` scans `$BATS_TEST_DIRNAME/*.bats`, so your new file is on its guarded surface: no bare `[[` or `((` as a statement in command position anywhere in it.
- `tests/helpers.bash` already provides `assert_contains` and `assert_not_contains`. Use them rather than writing new assertion primitives.
