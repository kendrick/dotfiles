## Spec excerpt

### The problem

`dotfiles-doctor` lists unresolvable and uninstalled entries under a heading that promises a retry the tool's model does not provide:

- `dot_local/bin/executable_dotfiles-doctor:17` — `-- in your dotfiles but not installed (next apply installs these):`
- `dot_local/bin/executable_dotfiles-doctor:58` — `-- in a bundle you've enabled but not installed (next apply installs these):`

The next apply usually will not. `run_onchange` records a script's hash once it completes, and the installer exits 0 by design (#17), so chezmoi treats it as done and skips it until the rendered input changes again. The hash comment at `run_onchange_install-packages.sh.tmpl:2-5` is the mechanism: the script re-runs when the rendered Brewfile changes, not when a package is still missing.

So a package can sit in that list apply after apply while the parenthetical insists it is about to be installed.

### What to build

Reword both parentheticals to describe what actually happens, and to tell the reader what to do about it. This was settled with the user: reword to match reality rather than adding a retry marker to make the promise true. Making `run_onchange` retry until it succeeds is a non-goal, settled in #17 and unchanged here.

Requirements:

- Both lines change. The VS Code list at `:17` has the same defect as the Homebrew list at `:58`, for the same reason.
- Deleting the parenthetical is not enough. The list is still there and the reader would have less idea than before what to do with it. Replace it with something actionable.
- Do not claim behavior the script does not have. The new wording is only an improvement if it is true.
- Match the file's voice. `dotfiles-doctor` is written as a read-only report that explains its own reasoning; the comments at `:25-32` and `:76-94` are the register to aim for.

### The constraint that will bite

`tests/doctor.bats:99` asserts:

```bash
assert_contains "in a bundle you've enabled but not installed"
```

That is the prefix before the parenthetical, so rewording the parenthetical alone leaves it passing. Change the prefix and you break it. If you have a reason to change the prefix, update that assertion in the same task — you own `tests/doctor.bats` — but the whole suite has to stay green either way.

### Scope

Do not touch `_working-memory/` either. T-003 owns it and updates it once the job lands; a write there from you or from T-001 would clobber the other's, and nothing in the wave can detect that.
