## Spec excerpt

### What this task is

The job's final pass. It runs the two whole-job checks that no single building task can run for itself, writes down what they said, and brings working memory up to date. It repairs nothing.

### 1. Run `bats tests/`, whole

The clean tree this job started from was 125 cases green, measured directly. T-001 adds four cases, so expect 129. Every existing case must still pass — in particular the five `install-packages` cases at `tests/install-failures.bats:74-181` and the bash 3.2 bare-compound guard in `tests/lint.bats`.

### 2. Check the diff scope

The working tree may touch only these five paths:

- `run_onchange_install-packages.sh.tmpl`
- `dot_local/bin/executable_dotfiles-doctor`
- `tests/install-failures.bats`
- `tests/doctor.bats`
- `_working-memory/`

`.chezmoidata.toml` must be unmodified. A package that vanished upstream gets reported for a human to rule on, never silently dropped — a stated non-goal of the whole job. `dot_claude/encrypted_private_settings.json.age` was already modified before this job started and is not ours; the check takes it as `--ignore`.

### 3. Write the verification report

Produce `.agent-guild/state/reports/T-003-verification.md` (create the directory if needed). Record, for each of the two checks: the exact command, its exit code, and the salient output — the bats pass/fail counts, and the diff-scope verdict with every path it listed. If something failed, name the failing case or the out-of-scope path exactly. This file is the task's artifact and the reason the report is a file rather than a chat message: the checker re-derives from it.

### 4. Update working memory

`AGENTS.md:34` obliges an update to `_working-memory/activeContext.md` and to any on-demand file the change touches, once a feature lands. Two of the three prior guild jobs in this repo carried this — #17 and #21 did, #19 did not. Record what shipped: the fetch-phase abort is fixed by drop-and-retry, and `dotfiles-doctor` no longer promises a retry `run_onchange` won't perform.

Read the rest of that section too, not just `:34`. Three further rules constrain how:

- **`decisionLog.md` is append-only (`AGENTS.md:36`): never edit a past entry.** `decisionLog.md:39` already anticipates this job — it records that #17's B-3 exemption was falsified and points at #22 for the remaining exposure. Answer it by **appending a new dated entry** that closes the loop `:39` opened. Leave the 2026-08-07 entry exactly as it is. `.agent-guild/state/archive/2026-08-08/tasks/T-008.md:45` is the precedent: decisionLog "gains a dated entry."
- **`activeContext.md` is a queue (`AGENTS.md:35`): evict completed items to `decisionLog.md`.** Its Current Focus is stale #17 content. Evicting that is part of this update, not a separate chore.
- **`activeContext.md` may not exceed 20 lines (`AGENTS.md:37`).** It is 21 lines right now, so appending without evicting first puts it further over. Land it under the cap.

This task owns `_working-memory/` outright. T-001 and T-002 are told not to touch it, so nothing else in the job writes there.

### If a check fails, report it — do not fix it

You own `_working-memory/` and your own report directory, and no source path in the repo. Repairing another task's artifact would hide which task broke it, and would put a write outside your `owns`. Name the failure in the report and return.

**For the orchestrator, since this is where it matters:** a FAIL on this task is almost never a defect in this task. T-003 executes two scripts; it cannot cause a red suite or an out-of-scope path. So a FAIL here is an **invalidation signal naming T-001 or T-002**, not a rework of T-003. Re-dispatching T-003's executor against the same broken tree returns the identical FAIL at every rung of the ladder and ends at "no rung above fable" with nothing repaired. Read the report, decide which dep's artifact is at fault, and run the invalidation path on that dep — diagnosis into *its* `## Rework diagnosis`, status to `rework`, `retries` incremented, same executor re-dispatched. Then re-run T-003.

### Why both of these clauses are parked here rather than on the building tasks

Not because a diff-scope check run from T-001 would flag T-002's writes — it would not. C-7's allowlist already contains all four wave-scope paths, so the check passes cleanly with every one of them dirty at once. The real reason is **attribution**: a stray write, or an edit to `.chezmoidata.toml` from either task, turns C-7 red on *both* tasks with nothing to say which one did it. A C-7 run from T-001's checker would rework T-001 for something T-002's worker wrote.

For C-4 the reason is different and simpler: `bats tests/` run from T-001's checker while T-002's worker is mid-edit of `dot_local/bin/executable_dotfiles-doctor` fails on a half-written file. The suite can only be trusted once the wave has landed.

### One environment hazard worth knowing

This repo is a chezmoi source directory and chezmoi walks it recursively for control files. Any scratch fixture containing a `.chezmoi*` file anywhere under the repo breaks `chezmoi execute-template` tree-wide, and most of the suite fails for reasons that have nothing to do with the job. It already happened once during this job's audit. Put scratch under `mktemp -d`, and if the suite fails oddly, run `chezmoi execute-template '{{ template "bundles" . }}'` to check the renderer before believing the results.
