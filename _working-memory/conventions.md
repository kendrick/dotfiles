## Naming
- chezmoi filename prefixes are load-bearing: `dot_` → `.`, `private_` → 0600, `executable_` → `+x`, `run_once_` → run once per machine, `run_onchange_` → re-run when content changes, `.tmpl` → Go-templated. _(git ls-files; README.md "How the automation works")_
- Commits follow Conventional Commits prefixes: `feat`, `fix`, `refactor`, `docs`. _(git log)_

## File Organization
- zsh config is split by concern under `~/.config/zsh/` (aliases, exports, functions, plugins, keybindings, options, styles), sourced from `~/.zshrc`. _(dot_config/zsh/, dot_zshrc.tmpl)_
- Exports that must reach non-interactive shells (cron, LaunchAgents, `ssh host cmd`) live in `dot_zshenv.tmpl`, not `exports.zsh`—zsh sources `.zshenv` for every shell, while exports.zsh only reaches interactive ones via zshrc. `JD_VAULT` is the case that forced the split; the template's own comment carries the vault-resolution rationale. Keep `.zshenv` to exports that genuinely need this, PATH and the rest stay put. _(dot_zshenv.tmpl; kendrick/skills#55)_

## Templating / Machine Conditionals
- Machine-specific content uses Go-template guards on `.machine_role` (e.g. `{{ if eq .machine_role "work" }}`) inside a single file, not branched files. _(dot_gitconfig.tmpl, .chezmoi.toml.tmpl)_
- Where the list of things being gated is long enough to be data, gate on membership instead: the item declares what it belongs to, the role only picks a default set, and the machine can override. Roles are a coarse lever, and a machine that wants one exception has nowhere to say so under a role branch. _(.chezmoidata.toml bundles; GitHub #4)_
- A `[data]` key added after a machine last ran `chezmoi init` isn't in that machine's config, and `chezmoi apply` doesn't regenerate it; it warns and carries on. So every read of a newer key needs a fallback, or the first apply after a pull dies with "map has no entry for key". Use `hasKey` when an empty value is legal; `| default` only when it isn't, since empty lists and strings are both falsy. _(.chezmoitemplates/bundles, .chezmoiignore)_

## Shared shell code
- Helpers used by more than one script live in `.chezmoitemplates/` and come in through a Go template include, which is what turns a plain `.sh` script into a `.sh.tmpl`. Never write the include call inside the partial itself: chezmoi parses partials as templates too, so it recurses. _(.chezmoitemplates/sh-ui.sh)_
- Interactive waits gate on `[ -t 0 ]`. Animation gates on `ui_watching`, which answers by opening `/dev/tty` rather than by testing stdout, so a human who pipes or captures an apply keeps the display while the capture keeps clean lines. No `-t 1` survives in executable code, and `tests/progress.bats` asserts that against the kit source. An unattended apply must still never block on a prompt, and the settled lines that reach stdout have to stay greppable, because the auto-sync log is a capture. _(.chezmoitemplates/sh-ui.sh, run_once_before_install-prerequisites.sh.tmpl; GitHub #37)_
- Every tool call made while a step is live goes through `step_run`. Without it the tool's output continues the live line's row: a frame write parks the cursor at the end of the drawn text and never emits a newline, and on an attended apply stdout and `/dev/tty` are the same device. `step_run` deliberately does not restart the ticker, so a step that ticks and immediately shells out is carried by its settled line and the tool's output instead of by the animation. A script using `step_begin_quiet` owns no live line and needs none of this. _(.chezmoitemplates/sh-ui.sh, run_onchange_install-vscode-extensions.sh.tmpl; GitHub #38)_
- The package installer draws a live line only while `brew bundle` has nothing to say. `spin_until_log_gate` runs it and stops at brew's first `Installing`, `Upgrading`, or `Using` line, which is where a cask's sudo prompt starts owning `/dev/tty`. Matching only `Installing` misses the upgrade case, and an upgrading cask is the entry most likely to ask for a password. The gate is one-way by construction: the only call that can draw sits ahead of the first `brew bundle`, and the retry inside `handle_bundle_result` has no path to it. While the line is up brew's output goes to `$bundle_log` alone and reaches stdout when the line comes down, so a capture still gets every byte. The entry count comes from reading the Brewfile against `brew list`, never from brew's own `Fetching` line, which brew has reworded across releases and suppresses under `--quiet`. _(.chezmoitemplates/sh-ui.sh, run_onchange_install-packages.sh.tmpl; GitHub #33)_
- Put anything interactive ahead of `step_begin`. A frame drawn over a prompt erases it, and the apply then blocks on a question the terminal showed for 100ms. restore-agent-skills hit this with `gh auth login`; brew's sudo prompt is the case C-13 was written for. _(run_onchange_after_restore-agent-skills.sh.tmpl; GitHub #38)_

## bash 3.2
- Scripts here run under `/bin/bash`, which is 3.2 on macOS, so no associative arrays and no `${var^^}`. Expanding an empty array under `set -u` (`"${arr[@]}"`) aborts rather than yielding nothing, so guard every expansion with `[ "${#arr[@]}" -gt 0 ]`. The count form is safe on empty; the expansion isn't. _(dot_local/bin/executable_dotfiles-teardown.tmpl, .chezmoitemplates/sh-ui.sh)_
- Under `set -e`, a failing `[[ ]]` or `(( ))` doesn't abort. The failure is discarded unless the construct is the enclosing function's literal last statement, so `f() { [[ 1 -eq 2 ]]; echo reached; }` prints `reached` and exits 0. A semicolon is no escape either (`true; [[ 1 -eq 2 ]]; echo reached` prints it too), which is why the rule is "never use either as a statement" rather than "never start a line with one". Loops are where it hides longest: `for i in 1 2 3; do [[ $i -ge 3 ]]; done` exits 0, so only the last iteration's result survives. `[ ]`, `grep`, and a function returning non-zero all propagate from every one of those positions. _(tests/helpers.bash; GitHub #21)_

## Teardown declarations
- Any script that leaves state on the machine declares it as `# teardown:<class> <path>` in its header, using a literal `~`. Classes: `secret` (removed by default), `data` (`--full` only), `none` (leaves nothing). Required on every `run_*` script and enforced by `dotfiles-doctor`; optional but read on `dot_local/bin/*`. _(dot_local/bin/executable_dotfiles-teardown.tmpl)_
- Don't add paths to a central list in the teardown script. Anything chezmoi can enumerate should be queried from chezmoi; anything it can't should be declared where it's created. _(decisionLog 2026-08-05)_

## Config-to-package coupling
- When a managed config names an external resource by string (a font family, a binary, a theme), the package registry needs a matching entry in a bundle the machine has on, or it fails only on a fresh machine where the resource was never hand-installed. Fonts are the case that's closed: every half of every `dot_config/font/registry.json` entry declares the casks it needs, and `dotfiles-doctor`'s "Config dependencies" section asserts an enabled bundle carries them. Anything else named by string is still unchecked. _(dot_config/font/registry.json, dot_local/bin/executable_dotfiles-doctor; GitHub #7, #4)_
- Declare the dependency next to the config that names it and have the checker read the declaration. Don't teach the checker to parse resource names out of configs and map them to package names: cask names don't track family names (`font-monaspice-*` ships `MonaspiceNe`), so a resolver is a second table to keep in sync. A declaration that's missing reports itself; a lookup table that's stale still looks correct. _(decisionLog 2026-08-05)_

## Scripts that rewrite a managed config
- Build the new content in a `mktemp` file and move it into place, so a failed run can't leave a half-written config. Then restore the target's mode: `mktemp` creates 0600, and a bare `mv` tightens the file enough that `chezmoi re-add` records it as a `private_` source entry, which renames it and turns one edit into a delete plus an add. Stat the target before the move, `chmod` after. _(dot_local/bin/executable_font `replace_preserving_mode`)_
- Write into a marker-delimited region (`# BEGIN x (managed by \`y\`)` … `# END x`) when the rest of the file is hand-edited, and treat a missing marker as a hard error rather than guessing where the block belongs. _(dot_config/ghostty/config)_
- Prefer an anchored line replacement over parse-and-reserialize when a formatter also owns the file. Serializing normalizes away whatever the formatter will just put back, so the file churns on every write. Anchor on the key, and fail if the anchor matches zero times or more than once. _(dot_local/bin/executable_font `write_vscode_key`, decisionLog 2026-08-05)_
- After mutating a managed file in `$HOME`, `chezmoi re-add` it. Without that the next `chezmoi apply` reverts the change, so the script looks like it worked until it silently doesn't.
- The same rule runs backwards, and that direction is the dangerous one: after editing a managed file in the chezmoi **source**, run `chezmoi apply` before the next `dotfiles-sync`. The sync's blanket `chezmoi re-add` captures the live copy back over the source and commits the reversion unattended, so a source edit left unapplied is deleted rather than merely ignored. This is how the #19 guard deleted itself (`ffc481d`). Applies to every managed file, not just the generated ones antipatterns 2026-06-15 covers. _(decisionLog 2026-08-09; GitHub #28)_
- Since the content-based guard shipped (`b047a75`), that gap refuses instead of destroying—but it refuses the **whole** sync, so an unapplied source edit now blocks every capture until someone applies. Treat a targeted `chezmoi apply` as part of shipping any change to a `$HOME`-bound script, in the same breath as the commit. Both `dotfiles-sync` and `dotfiles-doctor` needed one this way on 2026-08-20. _(decisionLog 2026-08-20)_

## Testing scripts with bats
- Assert with `assert_contains` and `assert_not_contains` from `tests/helpers.bash`, never with a bare `[[ ]]` or `(( ))`; the bash 3.2 bullet above is the why. All 54 bare compound statements in the suite are gone (#21). 53 of them were assertions and now call a helper; the 54th is `packages.bats`'s skip guard, `[ -n "$cask" ] || continue`, which is loop control rather than an assertion and stayed single-bracket because `[ ]` propagates. The suite's ~162 other `[ ]` assertions were left alone for the same reason. _(tests/helpers.bash, tests/packages.bats; GitHub #21)_
- `tests/lint.bats` fails the whole suite if a bare `[[` or `((` comes back in command position anywhere on `tests/*.bats`, `tests/helpers.bash`, or `tests/mutation-check.sh`. A compound used as an `if` or `while` condition is left alone on purpose: the branch consumes its exit status, so the bug can't reach it there. _(tests/lint.bats)_
- `tests/mutation-check.sh` inverts each assertion in turn and requires that case to report `not ok` in TAP. Run it after changing an assertion, and read its per-file counts rather than its total: a file that silently enumerates zero sites is exactly what a plausible-looking total hides. **Run it in the foreground, or backgrounded somewhere completion is tracked, and wait for it.** It edits the test file in place and restores through an `EXIT INT TERM` trap, so a run that never finishes leaves inverted assertions behind and anything reading the file meanwhile sees garbage. Budget the time instead of overlapping it: 45 sites on `doctor.bats` is about half an hour. _(tests/mutation-check.sh; antipatterns 2026-08-20)_
- One fixture proves almost nothing about generality. `zappy` was the only entry carrying a `min_macos` when #23 shipped, and an implementation that simply special-cased its name would have passed every obvious assertion. Pin the axis rather than the instance: a value below, exactly on, and above a boundary; an entry *without* the field riding through unchanged; and two entries differing on the field, which is what caught the held bucket printing its heading inside the per-entry loop. That defect was invisible with one held entry and repeated the whole heading with two. _(tests/packages.bats, tests/doctor.bats; GitHub #23)_
- Every test file opens with `load 'helpers'`. That is the only thing putting the two helpers in scope, and a new file that forgets it dies on its first assertion with a command-not-found. There is exactly one definition of each, in `tests/helpers.bash`; the local copies `install-failures.bats` used to carry are gone, because seven copies of an assertion helper is how their semantics drift apart. _(tests/helpers.bash)_
- Drive the real script as a subprocess against a fake `$HOME` with its external tools stubbed on `PATH`, and assert on exit codes and resulting file bytes. Don't reach in for helper functions, and don't assert on log wording as a stand-in for behavior: what usually matters is what the run left on disk and whether it refused when it should have. The exception is a script whose output _is_ the contract. The installers exist to name the item they couldn't install, so `tests/install-failures.bats` does assert on their wording, pinning the item's name plus enough of the line around it to tell a skip from a failure. _(tests/font.bats, tests/licensed-fonts.bats, tests/install-failures.bats)_
- `unset XDG_CONFIG_HOME` and `XDG_CACHE_HOME` in `setup()`. Both are set on this machine, and a script honoring them goes straight back to the real `~/.config` and `~/.cache` no matter what `$HOME` says. Every suite that fakes `$HOME` needs this; `licensed-fonts.bats` and `doctor.bats` were the last two to get it (#31).
- Render templates with `chezmoi execute-template --source "$SRC"` under a fake `$HOME`, and add `--config` when the template reads config data. Bare `execute-template` resolves its source dir from `$HOME/.local/share/chezmoi`, so under a synthetic `$HOME` it finds nothing and an include silently renders empty. `--source` fixes that half and cannot fix the other: `.chezmoitemplates/bundles` reads `machine_role` and `bundles` out of *config data*, which no `--source` supplies, so it falls back to `["core"]` and every cask outside the core bundle reads as a gap. Pin a role through a fixture config, the way `tests/packages.bats` does. _(tests/doctor.bats, tests/licensed-fonts.bats; GitHub #31)_
- The suite uses two PATH-stubbing idioms, and they are not interchangeable. `tests/sync.bats:53` replaces PATH (`export PATH="$STUBS:/usr/bin:/bin"`); `tests/doctor.bats:65` appends the inherited one (`export PATH="$STUBS:$PATH"`). Under the appending form, a case asserting a tool is **absent** cannot just skip writing its stub—the really-installed binary answers and the case quietly asserts the reverse of what it reads. Narrow PATH to the stub dir plus whatever that one case genuinely needs, which is what the `mas`-absent case does with a jq-only dir. _(tests/doctor.bats, tests/sync.bats)_
- zsh functions are testable from bats by sourcing the functions file in a real zsh: capture `REAL_ZSH="$(command -v zsh || true)"` at file scope before `setup()` replaces PATH, then `run "$REAL_ZSH" -c "source '$FUNCS'; fn"` with the function's external tools stubbed. When a payload's exact bytes matter (a clipboard that must carry no trailing newline), the stub writes stdin straight to a file (`cat >"$FILE"`) and assertions read it back with a sentinel—`"$(cat "$FILE"; printf x)"`—because a bare command substitution strips the very newline under test. _(tests/finder-copy.bats; GitHub #34)_
- `tests/mutation-check.sh` scans only its closed `ALL_FILES` list, #21's six converted files. New test files don't register there and don't need to; `lint.bats` is the only gate that auto-enrolls every `tests/*.bats`. _(tests/mutation-check.sh:67; decisionLog 2026-08-29)_
- Guard a capture-before-stub with `|| true`. `REAL_X="$(command -v x)"` at file scope runs under errexit, so on a machine without `x` the whole file dies at load instead of skipping the one case that needed it. `tests/helpers.bash:46-47` has it right. `tests/doctor.bats:20` still doesn't and now has a ticket, GitHub #32, which also covers the second instance at `tests/apps.bats:19`. _(tests/helpers.bash, tests/doctor.bats; GitHub #32)_
- Derive expected values from the data file or the fixture, never from what a managed config currently holds. A test pinning a live setting breaks the moment the thing under test starts owning that setting, which has happened twice. _(tests/font.bats)_
- Stub anything slow or machine-dependent (`system_profiler` takes ten seconds and answers about whichever machine is running the suite) and have the stub log its invocations, which is the only way to assert a cache was actually used.
- The progress venues capture the script's stdout separately from `/dev/tty`, and that separation is load-bearing: under a pty a combined capture cannot tell an animation drawn correctly to `/dev/tty` from one wrongly drawn to stdout. A case about those two streams colliding needs the opposite, so it passes `--stdout-to-tty` to `pty-run.py`, which leaves fd 1 on the pty slave. Assert `glyph_rows` and `marker_rows` are non-zero next to `violations`, or a capture that recorded no frames passes by holding nothing. _(tests/support/pty-run.py, tests/support/interleave-check.py, tests/progress.bats; GitHub #38)_
- A template that branches at render time needs its condition satisfied in the fixture, not at run time. `run_onchange_after_install-claude-plugins.sh.tmpl` stats `~/.config/chezmoi/key.txt` while rendering, so a venue with no age key renders a two-line early exit and the case runs against a script with no install calls in it. `ui_claude_plugins_venue` generates a throwaway keypair and encrypts its own fixtures to it. _(tests/helpers.bash; GitHub #38)_

## Error Handling
- Setup scripts use `set -e` for fail-fast, with one deliberate exception: the macOS-defaults script omits it, because several `defaults write` keys error on Sequoia and one failing key shouldn't abort the whole run. _(run_once_after_configure-macos.sh)_
- External-tool installers (`brew bundle`, `code --install-extension`, `claude plugin install`, `open raycast://`) never guard an install call with `|| true`. Under that guard a refused item printed nothing at all, so "the CLI isn't on this machine" and "the CLI ran and turned the item down" read identically. An absent tool prints a skip line naming it. A tool that ran collects what it couldn't install and names each one in a summary at the end, with the tool's own stderr left on screen so the reason survives next to the name. Both paths still exit 0: one stale extension id is no reason to abandon the rest of the apply, and `dotfiles-doctor` is what carries the gap forward. _(run_onchange_install-vscode-extensions.sh.tmpl, run_onchange_install-packages.sh.tmpl, decisionLog 2026-08-06)_
- A site reports only what it can observe. `open "raycast://extensions/install/<name>"` returns as soon as macOS accepts the URL, well before Raycast has fetched or built anything, so that script names the URLs macOS wouldn't pass along and stays silent about whether an extension installed. _(run_onchange_configure-raycast.sh.tmpl)_
- A notification points at the log; only the terminal output carries a runnable command. A macOS notification can't be piped anywhere, so a command inside one gets retyped by hand and errors, which teaches the reader to distrust the next one too. Every `notify_fail` site in `dotfiles-sync` names `$LOG` and nothing else, and the `echo` beside it is where the command lives. _(dot_local/bin/executable_dotfiles-sync; GitHub #27)_

## Cross-machine sync
- Capture local changes with `dotfiles-sync` (regenerates VS Code ext list, `chezmoi re-add`, commit + push); pull elsewhere with `chezmoi update`; spot drift with `dotfiles-doctor`; file a drifted package into a bundle with `dotfiles-apps --adopt`. Raycast extensions are still captured by hand. _(dot_local/bin/executable_dotfiles-sync, executable_dotfiles-apps)_
- A tool that edits config on the user's behalf keeps repo-wide edits and machine-local edits on separate screens, even when the data looks the same. `.chezmoidata.toml` changes every machine and gets committed; `chezmoi.toml` changes only this one and never does. Merging them into one picker is how someone reassigns a package for everybody while meaning to change one laptop. _(dot_local/bin/executable_dotfiles-apps, decisionLog 2026-08-06)_

## chezmoi ignore + source-only data
- `.chezmoiignore` matches TARGET paths (home-relative), not source paths. A source-name entry (`private_Library/…`, `dot_local/bin/executable_x`) silently no-ops — use the deployed path (`Library/…`, `.local/bin/x`) and verify with `chezmoi ignored`. _(.chezmoiignore, chezmoi ignored)_
- Files generated from live state, or rendered purely as data for a script, are source-only: `.chezmoiignore` the target so the daily `chezmoi re-add` can't clobber the freshly-generated source with a stale deployed copy. _(VS Code ext list; the Brewfile is rendered inline by the installer)_
- A dot-prefixed source entry (`.chezmoidata.toml`, `.chezmoitemplates/`, `.agent-guild/`) is source-only for free, since chezmoi never gives it a target, so it needs no `.chezmoiignore` line at all. The rule above is for entries that would otherwise deploy. _(.chezmoidata.toml)_
