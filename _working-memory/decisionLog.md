## 2026-08-05 — Registry entries declare their casks; doctor checks the declaration
**Context:** GitHub #7. Ghostty and VS Code both named `FantasqueSansM Nerd Font` while the Brewfile installed no fonts at all, and it went unnoticed for years because the files had been hand-dropped into `~/Library/Fonts` on the older machines. `dotfiles-doctor` couldn't have caught it: comparing installed against tracked is the right check on the wrong axis, and a hand-installed font satisfies neither side of it. The gap only surfaced on a fresh MacBook, as a p10k prompt full of replacement boxes.
**Decision:** Each half of each `dot_config/font/registry.json` entry carries a `casks` array, and a new "Config dependencies" section in `dotfiles-doctor` asserts the Brewfile has a `cask "…"` line for every one. Three states rather than two: a populated list is a claim to verify, `[]` means the font doesn't come from Homebrew and is legal only on Tier C, and a missing key is a roster entry nobody said where to get. The empty-versus-missing distinction is what stops "I declared nothing" from reading like "I need nothing". Two `font.bats` assertions enforce the shape, so a future roster entry can't land undeclared.
**Why declare rather than resolve:** the ticket proposed parsing `font-family` out of the configs and mapping display names to cask names through a lookup table. Two things killed it. The font feature had already moved every family name into the registry, so the configs are generated and parsing them reads a derived artifact. And the mapping is genuinely arbitrary (`font-monaspice-nerd-font` ships `MonaspiceNe`, `font-caskaydia-cove-nerd-font` ships `CaskaydiaCove`), so a resolver is a second table to keep in sync, and a stale one fails silently. A declaration that's missing reports itself.
**Scope held to fonts,** per the ticket. The section is named for the axis rather than for fonts so a future binary or theme check has somewhere to go, but nothing else is checked and nothing was built for it.
**Alternatives considered:** A `family|cask` table inside the doctor script — rejected, splits font knowledge across two files whose drift is exactly the silent kind this check exists to catch. A separate `provides.json` mapping cask to families — rejected, more faithful to how Homebrew works but adds a file and still needs system-font exclusions for `Menlo` and `Courier New`. Reporting casks in the Brewfile that no entry names — rejected, `font-lora` is there for document work and always will be, so it would cry wolf.

## 2026-08-05 — Licensed fonts fetch from 1Password, and never needed a patcher
**Context:** Five commercial fonts sat in `~/repos/my-fonts` as 51MB of paid licenses. This repo is public, so the bytes can't live here, but a fresh machine still has to end up with them installed.
**Decision:** Store one zip per family as a 1Password document in the Personal vault, tagged `fonts`, and track only the item titles in `.chezmoitemplates/licensed-fonts.txt`. A `run_onchange` script fetches on manifest change and installs to `~/Library/Fonts/Licensed/`. The tag is what keeps the manifest honest: `op item list --tags fonts` enumerates exactly what's fetchable, so a name that has drifted is visible rather than silently skipped.
**Why not encryption in the repo:** age ciphertext doesn't delta, so every version bump adds a full copy to history permanently, and publishing ciphertext to a public repo bets on the key never leaking across the life of that repo — a bet that loses retroactively. 1Password moves the trust boundary somewhere it already exists. There's also a bootstrap problem specific to this setup: decryption happens on the second apply, so a fresh machine would spend its first pass with a registry naming families that aren't installed.
**The patcher turned out to be unnecessary:** the spec called for fetch-then-patch through a Docker image or local FontForge, and this machine has neither. Two of the three fonts were already Nerd Font patched with full icon coverage, and the third takes the same `Symbols Nerd Font Mono` fallback six roster keys already use. So the Docker path, the FontForge fallback, and the probe choosing between them were deleted rather than built. If an unpatched licensed font ever arrives, that's a new ticket starting with `brew install fontforge`.
**Why the install subdirectory:** teardown declarations take one literal path, and `~/Library/Fonts` is shared with the brew-managed roster, so it can never be declared. macOS scans subdirectories (verified), so `~/Library/Fonts/Licensed/` still registers while staying separately removable. Declared `secret` rather than `data`: these belong to the person, not to a client machine being handed back.
**Alternatives considered:** One document per font file — rejected, 33 manifest lines for no gain. One zip for everything — rejected, a machine wanting one family would pull all 51MB. Keeping the fonts in a private second repo — rejected, another thing to clone and sync, and the licenses still end up on disk somewhere unmanaged.

## 2026-08-05 — Resolve availability from a cache, and refuse rather than write a font that isn't there
**Context:** The registry is machine-independent: it names every font that might be selected, on any machine. Whether a given font is installed is a machine question, and the answer differs per laptop. Conflating the two gives you either a roster that looks broken on a client machine or a switch that writes a family nothing can resolve.
**Decision:** The registry lists and a cache at `~/.cache/font/families` resolves. The cache is the `Family:` column of `system_profiler SPFontsDataType`, rebuilt when it's missing, when it's older than seven days, or when `--refresh` says so. `font <key>` checks it before touching either config and exits non-zero if the family isn't there, naming the font and its tier, and for Tier C adding that it comes from 1Password so the fetch may not have run. `--force` skips the check for the font you installed five minutes ago. Bare `font` shows every entry regardless of availability, marks the absent ones `(not installed)`, and exits 0.
**Why refusing is the correct failure:** naming a family macOS can't resolve isn't an error anywhere in the stack. macOS substitutes silently, the config stays valid, `chezmoi apply` succeeds, nothing exits non-zero, and the first thing that tells you is a terminal full of replacement boxes. By then you've relaunched Ghostty and you're debugging the wrong layer. A non-zero exit naming the tier is the only outcome that points at the next move: `brew bundle` for Tier A and B, the fetch script for Tier C.
**Why a cache at all:** `system_profiler SPFontsDataType` takes about ten seconds here and reports 339 families. Listing the roster is supposed to be something you do without thinking about it, and paying ten seconds for it would make the whole command feel broken. Seven days is a guess, with `--refresh` for when you know it's stale and `--force` for when you can't wait.
**Alternatives considered:** `fc-list : family` answers the same question in 0.02 seconds, which makes it worth writing down why it lost. fontconfig appears nowhere in the Brewfile and is on this machine only as a transitive dependency of cairo, harfbuzz, pango, poppler, and tesseract, so it would disappear the day one of those does. It also reports families as comma-joined alias lists (`VictorMono Nerd Font,VictorMono NF,VictorMono NF Obl`) rather than the verbatim strings the registry was copied from, and dataContracts already records that this build of `fc-query` reports no feature data. Checking after the write and rolling back was rejected: it opens a window where the two configs disagree, and a crash inside that window leaves them that way. Hiding absent entries from the listing was rejected because a client machine with no licensed fonts would read as a broken registry rather than as a normal machine.

## 2026-08-05 — Font switching is a data file plus a script, not chezmoi templates
**Context:** The `font` switcher has to change the same two values in two places, Ghostty's config and VS Code's settings. Templating both and driving them from `chezmoi.toml` data was the obvious first shape, since that's how this repo handles machine-varying content everywhere else.
**Decision:** Keep both configs plain-managed and mutate them in place from `dot_local/bin/executable_font`, with every family name living in `dot_config/font/registry.json` and nowhere else. The script writes, then calls `chezmoi re-add` on both files.
**Why not templates:** `chezmoi re-add` skips templates. Converting either config to a `.tmpl` would silently drop it from `dotfiles-sync` capture, so edits made on one machine would stop propagating and nothing would say so. The README already documents that exact failure for the Brewfile, which is what made it recognizable here. The `re-add` call is load-bearing for the opposite reason: without it the next `chezmoi apply` reverts both files, so a switch that skipped it would look like it worked until the next apply undid it.
**Also decided:** Ghostty's block is marker-delimited (`# BEGIN font (managed by \`font\`)` through `# END font`) so hand-edited settings elsewhere in the file stay off-limits, and a config missing either marker is a hard error rather than a guess about where the block belongs.
**Alternatives considered:** Templates plus `chezmoi.toml` data — rejected above. A single template rendering both files — rejected, same `re-add` problem twice over. Symlinking the configs to generated files — rejected, it's in antipatterns.md already for settings.json.

## 2026-08-05 — Read VS Code settings as JSONC, write them by anchor
**Context:** The `font` switcher has to read and rewrite VS Code's settings, which aren't strict JSON and won't become strict JSON. Prettier is the default formatter with format-on-save, so trailing commas come back on every save. #10 originally said to delete the ones in the file; that fix would have held until the next time anyone opened it. The ticket was written when there were two, and there were three by the time it was picked up. jq has no relaxed parsing mode and no plugin hook that could add one.
**Decision:** Read through `~/.config/font/jsonc.jq`, a `jq -Rs` filter that strips structural trailing commas and then parses. Write with a line replacement anchored to each font key rather than serializing the object back out. Commas are tolerated because the formatter owns them and they carry no information. Comments still fail the parse, because those someone wrote on purpose and stripping them unattended isn't the script's call.
**Why not round-trip:** jq emits strict JSON, so writing through it would strip the commas that format-on-save then restores, and the checked-in settings would churn three lines on every switch. A full `jq --tab` round-trip was diffed against the real file to size that: the commas are the only difference, with tab indentation and key order both surviving. Small, but it recurs forever and buys nothing. Anchored writes leave every byte the switcher didn't mean to touch where it was.
**Alternatives considered:** Deleting the commas and parsing strictly — rejected, the formatter re-adds them. A `sed 's/,\s*}/}/'` normalizer — rejected, it corrupts any string ending in `, }`, and `editor.fontFamily` is a comma-separated fallback chain, so the trap sits in the exact value the switcher rewrites. A node or json5 based JSONC parser — rejected, jq is a declared brew formula while node arrives only through nvm, a shell function a script must source before node exists at all.

## 2026-08-05 — Split the roster by half: patched statics for the terminal, variable builds for the editor
**Context:** Widening the roster to nine keys (#12) forced a choice the three-font version never had to make. Six of the nine ship both a pre-patched Nerd Font static and an unpatched variable build, and the registry can only name one family per surface.
**Decision:** Both, split by surface. Ghostty and VS Code's integrated terminal take the patched static; VS Code's editor takes the variable build with `Symbols Nerd Font Mono` as its fallback family. Six keys are split this way: maple, both monaspace keys, both recursive keys, cascadia, and lilex. Fantasque and Victor stay on the patched static everywhere, because neither has a variable build worth reaching for.
**Why it isn't a preference:** the Nerd Fonts patcher runs through FontForge, which can't round-trip `fvar` and `gvar`, so patching destroys the variable axes. Patched-or-variable is a genuine either/or. Ghostty gains nothing from live axes and would only pay for the fallback chain, while VS Code can drive both the axes and `dlig`. Anyone reading the registry cold sees the two halves naming different families and assumes a bug, which is what this entry exists to answer.
**What the axes actually buy:** more than expected, because two of these fonts have unhelpful defaults. Monaspace's variable build defaults to wght 200, so an editor entry with empty `variations` renders ExtraLight. Recursive defaults to MONO 0 and CASL 0, meaning a proportional sans — `'MONO' 1` is what makes it a code font, and `'CASL'` is the only thing separating the `recursive` and `recursive-linear` editor halves, since both name the family `Recursive`.
**What re-reading the variable builds' GSUB found:** Recursive's variable build carries no `calt` at all. It has `liga` and `dlig` where the `RecMono*` statics have `calt` and nothing else. Reusing the static's string on the editor half, which is what the ticket's table invites, would have produced a font that renders correctly with the feature silently inactive. Monaspace's variable build also adds `rlig` its static doesn't have.
**Stylistic sets stay out, with one exception:** ssXX features name themselves in the font's `name` table, and reading those names inverts the obvious assumption. Maple's ss01–ss11 and Lilex's ss01–ss04 are mostly named "Broken _X_ ligatures", so they turn ligatures off. Recursive's are letterform alternates and Cascadia's are unnamed. Only Monaspace's ss01–ss10 are ligature groups, so Monaspace is the one family that gets them in its feature string. Enabling every recorded set, which the ticket's fact table reads like an instruction to do, would have defeated ligatures on two of the nine fonts.
**Alternatives considered:** one family per key, variable everywhere — rejected, the terminal then needs a fallback chain for icons and Ghostty's chain handling is the thing the patch exists to avoid. One family per key, patched everywhere — rejected, it throws away the axes for nothing, and Recursive's Casual and Linear cuts stop being reachable from one family. A `tier` of `b` on the split keys rather than `a`: kept as `b` per #12's prose, though #8's schema example shows `a` for the same key; both resolve to "run `brew bundle`" in a refusal message, so the disagreement is cosmetic.

## 2026-08-05 — Phase 0 fonts: the ligature source never existed, so verify against the font binaries
**Context:** #9 specified filtering the roster by "the ligature YES/NO column" in the Nerd Fonts README. There is no such column. The YES/NO column is `*RFN`, Reserved Font Name, a licensing flag, and the legend saying so sits one line under the table. Fira Code and Hack both read NO, which is the proof: one is the canonical ligature font and the other ships none. The README carries no ligature information anywhere, so the filter the spec leaned on was never there to use.
**Decision:** Read GSUB feature tags straight out of the installed font files instead. A stdlib Python probe walks the sfnt table directory to the GSUB FeatureList and dumps the tags, which settles "does this family have ligatures" and "which feature string does it need" from one source that can't be out of date. Facts recorded in dataContracts.md; the probe is a throwaway, not a repo artifact.
**What it changed:** `blex` is struck from Tier A. `BlexMono Nerd Font` carries ss01 through ss07 and no `calt`, `liga`, `dlig`, or `rlig`, confirmed across the Mono variant and the Bold weight as well as the base Regular. Tier A drops from ten keys to nine. The per-family feature strings on #8 were guesses and mostly wrong: only Monaspace carries `liga`, Cascadia pairs `calt` with `rlig` rather than `liga` and has no ss01, and Victor, Lilex, Maple, Recursive, and Fantasque are `calt` only.
**Worth knowing downstream:** most of these fonts implement ligatures under `calt`, which is on by default, so a registry entry's feature string mostly exists to enable what's off (`dlig`, the `ssXX` sets) or to re-assert `calt` where an app disables it. Writing `calt` everywhere is harmless but says less than it looks like it does.
**Alternatives considered:** Querying each upstream font repo for its ligature claim — rejected, ten fetches and still secondhand. Installing fontTools for the parse — rejected, a dependency added for a one-time read the stdlib already covers. `fc-query` — tried first, this build reports no feature data.

## 2026-08-05 — Test the teardown's destructive path for real, and harden what it found
**Context:** `chezmoi destroy --force` and `chezmoi purge --force` had only ever run against stubs, which proved ordering but not that the commands behave as assumed. For a script whose whole value is being correct the one time you need it, that was the wrong gap to leave.
**Method:** a `chezmoi` shim pinning `-S/-D/-c/--cache` to a scratch tree, with a gate asserting `chezmoi source-path` resolves inside it before anything destructive ran. Both commands work non-interactively as documented. The real machine was verified untouched afterward.
**Bugs it found that stubs could not:** `/bin/bash` is 3.2, where expanding an empty array under `set -u` aborts, so a second run (or a machine with nothing left) crashed instead of reporting clean. Switching arg parsing to `while`/`shift` consumed `$@`, so the self-deletion re-exec relaunched bare and silently downgraded `--full --yes` to a dry run. `--help` was keyed to a hardcoded line range.
**Harness artifact worth recording:** an early run appeared to delete `$HOME` itself. It was the test layout: `chezmoi purge` removes the config file's *parent directory*, and the config had been placed at the root of a tree that also held the fake home and source. With the config in its own `~/.config/chezmoi/`, as on any real machine, nothing outside the intended set is touched. Re-tested with a realistic layout: `$HOME`, an unrelated top-level file, and `Documents/` all survived.
**Hardening added:** `--full` refuses to run while the source repo has uncommitted or unpushed work (`--force-dirty` overrides), because everything else is recoverable and a local-only commit is not. It also requires typing the hostname. Every removing run writes a receipt of resolved paths, checkable with `--verify`, which is the only way to audit a `--full` run once chezmoi is gone.
**Still true:** `--yes` has never been run against this machine, only against isolated trees.

## 2026-08-05 — Derive the teardown set from chezmoi; declare the rest at the source
**Context:** No way to strip this setup off a client machine, and the sensitive material is scattered across encrypted targets, the age key, the gh token, the SSO cache, sync logs, `chezmoi.toml`, and the source repo. The requirement was that it keep working as the repo changes, not just match today's inventory, since a hardcoded list would rot exactly the way the Nerd Font gap did. (GitHub #3)
**Decision:** Two sources of truth, no third. Encrypted targets come from `chezmoi managed --include=encrypted`, so an encrypted file added later is covered with no teardown edit. Everything chezmoi can't see is declared as `# teardown:<class> <path>` in whichever script creates it, with classes `secret` (default level), `data` (`--full` only), and `none` (explicit "leaves nothing"). `dotfiles-teardown` greps those out of the source tree; `dotfiles-doctor` flags any `run_` script that declares nothing, which is what stops the list falling behind.
**Why declarations beat a central list:** the knowledge sits next to the code that creates the state, so adding a credential and declaring it are the same edit. A central list is a second place to remember.
**Design constraints found along the way:** the auto-sync agent has to be booted out first or it can re-add and commit mid-teardown; `chezmoi purge` has to run last because it destroys the source tree the enumeration reads; the script deletes itself at `--full`, so it re-execs from a temp copy (bash reads scripts incrementally and would otherwise truncate); and a failed `chezmoi destroy` must skip the purge so a half-torn-down machine can still enumerate what's left.
**Scope:** apps stay. Homebrew, casks, MAS apps, macOS defaults, and `~/.nvm` are all left alone; uninstalling them is slow, partly needs sudo, and isn't what makes a machine sensitive. The deploy key is deleted locally but must be revoked on GitHub by hand, which the script says out loud rather than implying the machine is clean.
**Verification limit:** dry runs were confirmed inert on this machine; every destructive path was exercised against stubs in a scratch HOME. `--yes` has never been run for real at either level.

## 2026-08-05 — Name the agents the skill restore installs to, instead of `-a '*'`
**Context:** `run_onchange_after_restore-agent-skills.sh.tmpl` passed `-a '*'`, which reaches every agent in the `skills` CLI registry (75 slugs today). A couple of those, `eve` and `promptscript`, only support project-level skills, so a fresh-machine restore printed a "does not support global skill installation" warning per skill per agent, interleaved with the successful installs. Nothing failed, but it read like a wall of errors during the part of the bootstrap you're least able to judge. (GitHub #6)
**Decision:** Replaced the wildcard with an `AGENTS=(claude-code codex)` array and repeated `-a` flags. Claude Code is the only agent with real usage (66 skills); Codex has a directory and is plausible occasional use. Adding an agent is a one-word edit, and because the script is `run_onchange_`, editing it re-triggers the restore, which backfills from the lockfile on the next apply. Narrowing `-a` does not affect which skills are considered missing: that check probes `~/.agents/skills/<name>`, the agent-independent store.
**Flag traps worth keeping:** `-a` wants slugs (`claude-code`), not the display names `skills ls --json` reports (`Claude Code`). There's no command that lists valid slugs, but passing a bogus one makes the CLI print the whole set: `npx skills ls -g -a x`. Comma-joining fails for both `-a` and `-s` (read as one literal slug); repeated flags are the form that works for both, though `-a` also accepts a space-separated list where `-s` doesn't.
**Not done:** skills already registered against ~59 agents stay registered, and stray symlinks under `~/.gemini`, `~/.cline`, `~/.config/opencode` stay too. Unwinding that needs `skills remove -a ...`, which is destructive and wants its own decision.

## 2026-08-04 — Install 1Password in the before phase and wait for the CLI integration
**Context:** On a factory Mac the age-key script installed only the `1password-cli` cask, then immediately ran `op read`. The desktop app arrives from the Brewfile a phase later, so `op` had no desktop integration to authenticate against: the read failed and the script printed instructions pointing at a Developer setting inside an app that wasn't installed yet. (GitHub #2)
**Decision:** The age-key script installs both casks (`--adopt`, so an app someone dragged in by hand doesn't cause a conflict), opens 1Password, and blocks up to 10 minutes while you sign in and switch on Settings > Developer > Integrate with 1Password CLI. Readiness is probed with `op account list --format=json` rather than `op read`, because a read fires Touch ID on every call and polling it would put a biometric prompt on screen every couple of seconds. The wait is gated on `[ -t 0 ]` so a non-interactive apply falls straight through. Terminal chrome moved into `.chezmoitemplates/sh-ui.sh` so both before-phase scripts share one copy, which turned `run_once_before_install-prerequisites.sh` into a `.tmpl` and re-runs it once per machine (harmless: both its branches short-circuit when CLT and brew are present).
**Does not change:** the two-apply requirement. `.chezmoiignore` is evaluated before any `run_before` script, so the encrypted Claude config still can't decrypt on the first pass.
**Alternatives considered:** `OP_SERVICE_ACCOUNT_TOKEN` for a fully headless fetch, rejected because it trades the GUI step for a long-lived token that still has to reach the machine somehow. Scripting the Developer toggle, not possible: 1Password keeps it in signed group-container settings on purpose. Install-and-inform with no wait, rejected because it leaves the bootstrap half-done when a 30-second pause would finish it.

## 2026-08-03 — Clone with chezmoi's builtin git; install Xcode CLT interactively
**Context:** The documented one-liner died on a factory Mac. `chezmoi init` shells out to `/usr/bin/git`, which on a machine with no Command Line Tools is a stub that fires the CLT installer and exits 1, so the clone failed before any `run_` script existed. `useBuiltinGit` defaults to `auto`, and auto only checks whether `git` is on `$PATH` — the stub is. All terminal chrome is gated on `[ -t 1 ]` so the auto-sync log stays plain.
**Alternatives considered:** A separate curl-able `scripts/bootstrap.sh` ahead of chezmoi — rejected, a second hosted entry point to remember for a problem one flag solves. GUI-only install — rejected, the download progress stays trapped in Apple's window. Headless-only — rejected, `softwareupdate -l` wording has changed across releases and there'd be no recovery when the label doesn't parse.

## 2026-06-25 — Provision the age key from 1Password at init; skip encrypted config until it lands
**Context:** The age-encrypted Claude config (settings.json + plugin manifests) needs `~/.config/chezmoi/key.txt` before chezmoi can decrypt it, and chezmoi decrypts `encrypted_` targets unconditionally on apply — so a fresh machine with no key aborted the whole run on the first one.

Closes the earlier "fresh machine needs the key first" risk.
**Alternatives considered:** Manual `op read` before init — rejected, easy to forget and it aborts apply if skipped. _(commits 6d505c4, 1e4f2a8)_

## 2026-06-15 — Source-only generated data; stop deploying files nothing reads

## 2026-06-13 — Encrypt settings.json; flag template drift re-add can't capture
**Context:** Follow-on from the plugin backup. settings.json was tracked as a template, but `chezmoi re-add` can't reverse-render a template, so it silently skipped the file. Claude rewrites settings.json constantly, so the live copy drifted far ahead of source and the daily sync never noticed. The only template-able content was the home-dir path; the rest is literal.
**Decision:** Encrypt settings.json (drop the `.tmpl`) so re-add captures it again — re-encrypting keeps the work-only plugin names private, and it resurrects the SessionStart hook that re-adds settings.json each session, so permissions auto-capture hands-off. Same age key as the plugin manifests. For files that must stay templated (`.zshrc`, `.gitconfig`, Brewfile), re-add will always skip them, so dotfiles-doctor and dotfiles-sync now detect and report template drift instead of silently dropping it.
**Alternatives considered:** Keep it a readable template and reconcile by hand — rejected, reintroduces the manual capture dotfiles-sync exists to kill. Encrypt only the private bits via an injected fragment — rejected, a file is template-or-not wholesale, so any template still wouldn't auto-capture. A custom scrub-and-templatize capture script — rejected for now, a scrub bug leaks permanently to a public repo, where encryption can't.

## 2026-06-13 — Back up Claude Code plugins (encrypted) like skills
**Context:** Plugin state had no cross-machine backup. A first pass tracked the two manifests as `create_` files, which `chezmoi re-add` skips, so the daily sync never captured new installs. The manifests and settings.json.tmpl also carried a work-only marketplace's repo and plugin names in plaintext, and this repo is public.
**Decision:** Mirror the skills setup (daily re-add captures the manifests; a manifest-driven run_onchange replays them on a fresh machine), but age-encrypt the manifests so the work-only names stay out of the public repo. The run_onchange decrypts at render time and gates installs by a public-marketplace allowlist, so personal machines get public plugins only and the committed template names no private org. Added a `claude()` wrapper mirroring `skills()`. Forward-only: prior plaintext stays in git history; version reproduction is fuzzy (install grabs latest vs the recorded SHA, self-heals on re-add).
**Alternatives considered:** Plaintext manifests with a capture-time filter to scrub work-only entries — rejected, fights the blanket re-add. A separate private overlay repo — rejected, second repo to sync and still needs the filter. Accepting the exposure — rejected by preference, though the marketplace repo is SSO-gated.

## 2026-06-07 — Add dotfiles-sync / dotfiles-doctor for cross-machine sync
**Context:** Repo is the source of truth, but capturing edits back was manual and easy to forget, and `chezmoi update` only adds — it never removes extensions/packages dropped on another machine.
**Decision:** Added `dot_local/bin/executable_dotfiles-{sync,doctor}`. `dotfiles-sync` regenerates the VS Code extension list, bare `chezmoi re-add`s all changed files, reports Brewfile drift, then commits + pushes. `dotfiles-doctor` is a read-only drift report for the receiving end (installed-but-not-listed = removal/capture candidates).
**Alternatives considered:** chezmoi `autoCommit`/`autoPush` — rejected (generic off-convention commit messages, no review gate); settings.json symlink and `brew bundle dump` — rejected (see antipatterns). _(commit 383e75e)_
